# The video tracker

The tracker is the source of truth for the whole video programme: every planned Orchard Core video, its status, and
who is working on it. [TRACKER.md](../TRACKER.md) at the repository root is the dashboard generated from it.

| File | What it is |
| --- | --- |
| `videos.json` | One entry per video (below). Changed with `tools/tracker.py set`, never by hand except to plan |
| `series.json` | The series in the order they are worked on, each with its learning path and a description |
| `NO-VIDEO.md` | The catalog entries that get no video, and why |
| `COVERAGE.md` | Every catalog entry and the videos that cover it (generated by `tracker.py report`) |
| `SPEC-QUESTIONS.md` | Questions about the skill's specification, raised while planning or writing videos |

## A video

```json
{
  "slug": "media-library-basics",
  "title": "Media Library: Upload, Organize and Reuse Files",
  "series": "Media",
  "order": 2,
  "audience": "admin",
  "priority": 1,
  "features": ["OrchardCore.Media"],
  "docs": ["src/docs/reference/modules/Media/README.md"],
  "status": "planned",
  "estimatedMinutes": 5.5,
  "words": 0,
  "contentCommit": "", "recordedBy": "", "recordedOn": "", "reviewedBy": "", "pullRequest": "",
  "release": "", "youtubeId": "", "publishedOn": "", "notes": ""
}
```

| Field | Meaning |
| --- | --- |
| `slug` | The video's permanent name: its folder (`videos/<slug>/`), its storyboard `output`, and its docs markers. Lowercase kebab-case, the feature first. **It never changes once the folder exists.** |
| `title` | The YouTube title without the `\| Orchard Core` suffix that `video.json` adds (so at most 85 characters here). |
| `series`, `order` | The series (a playlist, see `series.json`) and the video's place in it. |
| `audience` | `admin` (site owners, editors, administrators: the admin UI and the front end, no code on screen) or `developer` (module and theme authors: code, configuration and API slides). Never both in one video. |
| `priority` | 1 core and most used, 2 common, 3 niche. Videos are written and recorded in priority order. |
| `features` | The catalog entries (`catalog/features.json` ids) the video covers. |
| `docs` | The documentation pages it backs, relative to the root of `OrchardCMS/OrchardCore`. |
| `status` | See the lifecycle below. |
| `estimatedMinutes`, `words` | The planned length; once a storyboard exists, the words of its narration and the minutes at 150 words a minute. |
| `contentCommit` | The last commit that changed the video's folder when its content became ready. |
| `recordedBy`, `recordedOn` | Who recorded it, and when it was recorded. |
| `reviewedBy` | Who reviewed and merged the recording. |
| `pullRequest` | The pull request of the recording. |
| `release`, `youtubeId`, `publishedOn` | The GitHub release (`<slug>/vN`) that published it, its YouTube id, and the date. |
| `notes` | Why a video is blocked or needs an update, and other notes, dated. |

## The lifecycle

| Status | Meaning |
| --- | --- |
| `planned` | In the plan; content not written yet |
| `content-draft` | Storyboard, video.json and recording plan written, not validated |
| `content-ready` | Validated; ready for someone to record |
| `recording` | A session is recording it (set `recordedBy`) |
| `recorded` | Assembled and checked, MP4 exists outside git |
| `in-review` | Pull request open (set `pullRequest`) |
| `merged` | Folder merged to `main`, release not published |
| `published` | On YouTube (set `youtubeId`, `publishedOn`) |
| `needs-update` | The feature changed; the video must be revised (say why in `notes`) |
| `blocked` | Cannot proceed (say why in `notes`) |

What moves a video from one status to the next:

| From | To | When | Command |
| --- | --- | --- | --- |
| `planned` | `content-draft` | You start writing `videos/<slug>/` | `tracker.py set <slug> content-draft` |
| `content-draft` | `content-ready` | `python tools/validate_content.py <slug>` passes. `set` runs it, and refuses otherwise; it records the words and minutes | `tracker.py set <slug> content-ready` |
| `content-ready` | `recording` | A session starts recording it | `tracker.py set <slug> recording --by <name>` |
| `recording` | `recorded` | The video is assembled and checked for private data (OCR), and the MP4 is kept outside git | `tracker.py set <slug> recorded` |
| `recorded` | `in-review` | The pull request with the recorder scenes, `durations.json`, captions and thumbnail is open | `tracker.py set <slug> in-review --pr <url>` |
| `in-review` | `merged` | The pull request is merged to `main` | `tracker.py set <slug> merged --by <reviewer>` (or `tracker.py sync`) |
| `merged` | `published` | The release is published and the **Publish video** workflow wrote the YouTube id to `video.json` | `tracker.py sync` (or `set <slug> published --youtube <id>`) |
| any | `needs-update` | The feature changed, so the video says something that is no longer true | `tracker.py set <slug> needs-update --note "<what changed>"` |
| any | `blocked` | Something outside the video stops it (an external service with no stand-in, a bug) | `tracker.py set <slug> blocked --note "<why>"` |
| `needs-update` | `content-draft` | You revise the content | `tracker.py set <slug> content-draft` |

`set` refuses a jump that skips a step (`planned` straight to `recording`, for example) unless you add `--force`, and a
`blocked` or `needs-update` without a `--note`. Going back a step is always allowed.

## Working on videos

Every session that writes or records videos follows the same routine:

1. Read [TRACKER.md](../TRACKER.md), and pick the next videos: `python tools/tracker.py next --status planned` for the
   next to write, `python tools/tracker.py next` for the next to record (`content-ready`, in priority and series order).
2. Mark each one when you start (`tracker.py set <slug> content-draft`, or `recording --by <name>`).
3. When a video is done: `python tools/validate_content.py <slug>`, then `tracker.py set <slug> <status>`, and commit
   the video's folder with its entry in `tracker/videos.json`.
4. **A pull request holds one video**: `videos/<slug>/` and that video's entry in `tracker/videos.json`, nothing else.
   `TRACKER.md`, `tracker/COVERAGE.md`, `catalog/DOC-ISSUES.md` and `tracker/SPEC-QUESTIONS.md` are shared by every
   video, so a video's pull request leaves them alone (two pull requests that change them would conflict). Run
   `python tools/tracker.py report` in a pull request of its own to refresh the dashboard, and record a documentation
   issue or a question about the specification in the same way, or in the pull request description. The **Tracker**
   workflow runs `validate_content.py` and `tracker.py validate` on every pull request, and `report --check` when run
   by hand.
5. After a video's pull request is merged, `python tools/tracker.py sync` fills in what only the merged history knows
   (`contentCommit`, `merged`).

Sessions working in parallel each take a series, touch only their series' `videos/<slug>/` folders and
`tracker/videos.json`, and pull and merge before every push; nobody rebases a shared branch.

### The files of a video's content

Each video's folder holds `storyboard.json`, `video.json`, `recording-plan.md`, `README.md`, `slides.py` when the
storyboard has slides, and `OPEN-QUESTIONS.md` when something couldn't be verified. In `recording-plan.md`, every step
of a `clip` has an entry that names it in backticks (`` `create-1` ``): that is how `validate_content.py` matches the
plan to the storyboard. The recording sessions add `recorder/Scenes*.cs`, `durations.json`, the captions and
`thumbnail.jpg`.

## How the plan was made

The plan groups the catalog into 22 learning paths (the `path` of each series in `series.json`), from Getting Started
and Setup to Build a Site; each path holds one or more series, and each series is a YouTube playlist.

- A large module gets a series: an overview, then one video per task or screen.
- A screen whose content is code (Templates, Admin Templates, Placements, Shortcode Templates, Queries, GraphiQL) is
  shown in `developer` videos, because an `admin` video never shows code.
- A feature that needs an external service is planned with a local stand-in (an SMTP catcher, Azurite, MinIO,
  Elasticsearch, Redis, ClamAV in Docker, or a second tenant as the remote site), named in the video's `notes`. Where
  no stand-in exists (Azure AI Search, Azure Key Vault, Azure Communication Services), the video shows the settings
  with fake values and stops before calling the service, or stays `blocked`.
- Every catalog entry maps to at least one video, or to a reason in `NO-VIDEO.md`; `tracker.py validate` checks it, and
  `COVERAGE.md` shows the mapping.
